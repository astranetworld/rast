# N42 transaction type 0x50: alternative-signature transaction (AltSig)

Status: draft for phase 1 of `docs/ROADMAP_ED25519_TX.md` (2026-09-06). Call-only.

## Purpose

A typed transaction ([EIP-2718]) whose sender is authenticated by a signature algorithm
other than secp256k1 ECDSA, so the fleet's supply-side signature work can move to a
scheme with batch verification. The first algorithm is Ed25519. The type carries the
public key: these schemes do not recover it from the signature.

The algorithm identifier and the address derivation follow [EIP-7932] so that a later
alignment with Ethereum's registry is a renumbering, not a redesign.

## Encoding

```
0x50 || rlp([chain_id, nonce, max_priority_fee_per_gas, max_fee_per_gas, gas_limit,
             to, value, input, access_list, alg_type, pubkey, signature])
```

| field | type | rule |
| --- | --- | --- |
| `chain_id` | u64 | must equal the chain's id |
| `nonce` | u64 | as EIP-1559 |
| `max_priority_fee_per_gas`, `max_fee_per_gas` | u128 | as EIP-1559 |
| `gas_limit` | u64 | as EIP-1559 |
| `to` | 20-byte address | **required**; contract creation is not supported by this type |
| `value` | u256 | |
| `input` | bytes | |
| `access_list` | as EIP-2930 | |
| `alg_type` | u8 | `0x01` = Ed25519; any other value is invalid (`0x00` is reserved for secp256k1, `0x7F` is invalid, per EIP-7932) |
| `pubkey` | bytes | Ed25519: exactly 32 bytes, the compressed Edwards point |
| `signature` | bytes | Ed25519: exactly 64 bytes, `R || s` |

Transaction hash: `keccak256(0x50 || rlp([...]))` over the full list above, as for every typed
transaction. In a block body the transaction is an RLP string holding those bytes; in the
transactions trie it is the raw typed bytes. A receipt for a 0x50 transaction is encoded as
`0x50 || rlp(receipt)` and reports `type: 0x50` over RPC.

## Signing

```
signing_hash = keccak256(0x50 || rlp([chain_id, nonce, max_priority_fee_per_gas, max_fee_per_gas,
                                       gas_limit, to, value, input, access_list, alg_type, pubkey]))
signature    = Ed25519_sign(secret_key, signing_hash)      // the 32-byte hash is the message
```

## Sender

```
sender = keccak256(alg_type || pubkey)[12..32]
```

There is no recovery. The sender is a pure function of the key the transaction carries, so
every node derives it the same way, and the same Ed25519 key always maps to the same account.

## Validity (consensus rule)

A 0x50 transaction is valid iff all of the following hold. The rule is stated in terms of the
cofactored Ed25519 verification equation so that batch verification and single verification
accept exactly the same set of signatures (mixed-order points are where cofactorless and
cofactored verifiers disagree, and a chain cannot afford two answers).

1. `alg_type == 0x01`, `len(pubkey) == 32`, `len(signature) == 64`, `to` present.
2. `pubkey` decodes to a point on the curve and is **not** of small order (`is_weak() == false`).
3. `s` (the second half of the signature) is canonical: `s < L`.
4. The cofactored equation holds: `[8](s·B) == [8](R) + [8](k·A)` with `k = SHA-512(R || A || signing_hash)`.

Implementation: `ed25519_dalek::verify_batch` (which is cofactored) over any batch size,
including a batch of one; a batch that fails is retried transaction by transaction, so the
per-transaction verdict never depends on batch composition. `verify_strict` is **not** the
rule: it is cofactorless, and a signature could pass a batch and fail it.

Encoding-level rules (before any curve arithmetic): decoding rejects a list with the wrong
arity, a `to` that is not 20 bytes, and a pubkey or signature of the wrong length.

## Gas

Intrinsic gas is that of an EIP-1559 transaction with the same `input` and `access_list`
(21,000 for a plain transfer). The extra 96 bytes of key and signature are not priced: this is
a fleet-internal type on a chain whose block limit is measured in transactions, not bytes.
Fee semantics (`effective_gas_price`, base fee interaction) are EIP-1559's.

## Mempool

- Admission: decode, rules 1-4 above, then the ordinary nonce/balance/fee checks with the
  derived sender. Ingest paths verify in batches (`N42_ED25519_BATCH`, default 64).
- A 0x50 transaction and a secp256k1 transaction from the *same* account cannot exist: the
  account of an Ed25519 key has no secp256k1 private key. Nonce ordering is per account as usual.
- Not broadcast over devp2p transaction gossip in phase 1 (the fleet runs with tx gossip off);
  the type is reachable through `eth_sendRawTransaction` and the ingest channel.

## Execution

The EVM sees an ordinary call from `sender` with the fields above; `tx_type` is presented to
revm as `2` (EIP-1559 semantics). The plain-transfer fast path applies when `input` is empty
and `access_list` is empty. Nothing in execution depends on the algorithm.

## Chain activation

Enabled only on chains whose genesis `config` carries `"altSigTx": true`
(`n42_fleet7.json`, `n42_fleet7_bench.json`). Elsewhere the type is rejected at decode time.
gov5 does not recognise 0x50; a mixed fleet cannot carry it.

## Test vectors

`crates/n42/tx-types/testdata/altsig_vectors.json`: three transactions (plain transfer, transfer
with input, with access list) with the secret key, the signing hash, the signature, the sender
and the full encoded bytes, generated by the crate's own signer and checked by an independent
Python script (`docs/sigbench/altsig_vectors.py`).
